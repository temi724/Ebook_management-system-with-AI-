1. System Overview

The AI-Powered E-Library Management System is a web application that digitises the core operations of a university library: cataloguing books, managing the borrowing lifecycle, and helping readers discover relevant material through artificial intelligence. It serves four classes of user — Administrators, Librarians, Faculty, and Students — each with permissions appropriate to their role.

The platform is split into two independently deployable applications that communicate over a versioned REST API:

  • Backend (API server): a Python FastAPI application backed by a MySQL database, responsible for all business logic, persistence, authentication, and the AI recommendation pipeline.
  • Frontend (client): a React single-page application that consumes the API and presents a responsive, role-aware user interface.

3. System Architecture

The system follows a layered (clean) architecture on the backend, enforcing a strict separation of concerns. Each request flows through clearly defined layers, which makes the code testable, maintainable, and easy to reason about.

┌──────────────────────────────────────────────────────────────┐ │ React SPA (Browser) │ │ Pages → Zustand Stores → Axios Service Layer │ └───────────────────────────┬──────────────────────────────────┘ │ HTTPS / JSON (REST, /api/v1) ▼ ┌──────────────────────────────────────────────────────────────┐ │ FastAPI Application │ │ │ │ Endpoints (routing, HTTP) ← validates with Pydantic │ │ │ │ │ ▼ │ │ Dependencies (auth / RBAC guards) │ │ │ │ │ ▼ │ │ Services (business logic) ──────────► AI Service (RAG) │ │ │ │ │ │ ▼ ▼ │ │ Models (SQLAlchemy ORM) ChromaDB + Ollama │ └───────────────────────────┬──────────────────────────────────┘ │ SQL (PyMySQL) ▼ ┌───────────────┐ │ MySQL DB │ └───────────────┘

Design rationale. By routing every operation through a service layer rather than placing logic in the endpoints, the same business rules can be reused (e.g. by the seed script or future scheduled jobs) and tested in isolation from the HTTP layer.

4. Data Model & Database

Persistence uses MySQL via SQLAlchemy. A connection pool is configured with pool_pre_ping=True (to transparently recover stale connections), a pool size of 10, and an overflow of 20, enabling the API to serve concurrent requests efficiently. The schema is composed of four related entities.

Entities

TableKey fieldsPurpose
usersid, email, username, full_name, hashed_password, role, department, is_activeAccounts and role assignment. Passwords are never stored in plaintext.
booksid, isbn, title, author, category, description, tags, total_copies, available_copies, rating, is_activeThe catalogue. available_copies is decremented/incremented through the loan workflow.
loansid, user_id (FK), book_id (FK), loan_date, due_date, return_date, status, renewal_count, qr_codeOne borrowing record, advancing through a state machine. Stores a base64 QR image once approved.
reading_historyid, user_id (FK), book_id (FK), read_date, rating, reading_time_minutesCaptures reading patterns to drive personalised recommendations.

Relationships

  • A User has many Loans and many ReadingHistory entries.
  • A Book has many Loans and many ReadingHistory entries.
  • Deleting a user or book cascades to its related loan and history records (cascade="all, delete-orphan"), preserving referential integrity.
Soft deletes for books. Books are never physically removed; deletion sets is_active = False. This preserves the historical integrity of past loans that reference the title while hiding it from the active catalogue.

5. Authentication & Security

Security is implemented across several layers: password protection, token-based stateless authentication, role-based authorisation, and transport/configuration controls.

5.1 Password Protection

Passwords are hashed with bcrypt (via passlib's CryptContext) before storage. Only the resulting hash is persisted in the hashed_password column — the plaintext password is never written to the database or logs. Verification is performed by re-hashing the supplied password and comparing against the stored hash.

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def get_password_hash(password): return pwd_context.hash(password)
def verify_password(plain, hashed): return pwd_context.verify(plain, hashed)

5.2 Stateless Authentication (JWT)

On successful login, the server issues a signed JSON Web Token (JWT) containing the user's ID (sub) and an expiry claim (exp). The token is signed with the HS256 algorithm using a server-side secret key. Because the token is self-contained and signed, the server does not need to store sessions — every subsequent request is authenticated by verifying the token's signature and expiry.

to_encode = {"exp": expire, "sub": str(user.id)}
token = jwt.encode(to_encode, settings.SECRET_KEY, algorithm="HS256")

Tokens expire after a configurable window (default 30 minutes). Protected endpoints declare a dependency on get_current_user, which decodes and validates the token on every call; an invalid, tampered, or expired token yields 401 Unauthorized.

5.3 Role-Based Access Control (RBAC)

Authorisation is enforced through a hierarchy of FastAPI dependencies. Endpoints opt into the level of access they require, and the dependency raises 403 Forbidden if the authenticated user's role is insufficient.

Guard dependencyAllowsUsed by (examples)
get_current_userAny authenticated userBorrow a book, view my loans, request recommendations.
get_current_active_userAuthenticated & activeBase guard layered beneath the role guards.
get_current_librarianLibrarian or AdminCreate/update/delete books, approve loans, confirm returns.
get_current_adminAdmin onlyAdministrative user operations.

5.4 Transport & Configuration Controls

  • CORS: a Cross-Origin Resource Sharing policy restricts which front-end origins may call the API (configured via the BACKEND_CORS_ORIGINS setting).
  • Externalised secrets: sensitive values (database URL, secret key, token lifetime) are read from environment variables / a .env file rather than hard-coded, using Pydantic Settings.
  • Input validation: every request body is validated by a Pydantic schema, rejecting malformed payloads before they reach the business logic.
  • SQL-injection resistance: all database access goes through the SQLAlchemy ORM with parameterised queries, never string-concatenated SQL.
Production hardening note. The repository ships a development default SECRET_KEY and permissive database credentials for ease of local setup. For a production deployment these must be replaced with a strong, randomly generated secret and a least-privilege database account, and the API should be served strictly over HTTPS.

7. The Loan Workflow (with QR Verification)

Rather than a naive instant-checkout, the system models borrowing as an explicit state machine that mirrors how a physical library counter operates: a student requests a book, a staff member approves it, the student collects it using a verification QR code, and the return is likewise confirmed by staff. This keeps the digital record and the physical book in sync.

STUDENT SYSTEM / STAFF ─────── ────────────── request borrow ───────────► PENDING (no copy deducted yet) │ staff approve ───┤──► APPROVED → QR code generated, │ available_copies − 1 staff reject ───┘──► REJECTED │ collect book using QR │ ▼ "I returned it" ───────────► RETURN_REQUESTED │ staff confirm ───┴──► RETURNED → available_copies + 1 (background) past due_date ─────────► OVERDUE

Figure 2 — Loan state machine.

Key Design Decisions

  • Copies are reserved on approval, not on request. A pending request does not decrement availability; only an approved loan does. This prevents speculative requests from locking up stock.
  • Duplicate-request prevention. A user cannot hold two concurrent active or pending requests for the same title — the service rejects the second with a clear error.
  • QR-code verification. On approval, the server encodes the loan details (loan ID, book, borrower, due date) into a JSON payload and renders it as a base64 PNG QR code stored on the loan. The borrower presents this at the counter to collect the book, linking the digital approval to the physical handover.
  • Two-sided return confirmation. The borrower marks a return, but availability is only restored once staff confirm it — avoiding inventory drift from unverified returns.
  • Bounded renewals. Loans may be renewed up to a fixed maximum and cannot be renewed once overdue.
  • Consistency guard. The update_available_copies routine refuses any change that would push the count below zero or above the total, protecting the invariant 0 ≤ available_copies ≤ total_copies.

8. AI Recommendation Engine (RAG Pipeline)

Book discovery is powered by a Retrieval-Augmented Generation (RAG) pipeline. RAG combines a semantic search step (retrieval) with a language model (generation), so that recommendations are grounded in the library's actual catalogue rather than the model's general knowledge. The entire pipeline runs locally via Ollama, requiring no external paid API.

┌── INDEXING (build the knowledge base) ───────────────────────┐ │ Books → rich text (title, author, category, description, │ │ tags, publisher, year) │ │ → embeddings (all-MiniLM-L6-v2, 384-dim) │ │ → stored in ChromaDB vector collection │ └──────────────────────────────────────────────────────────────┘ ┌── QUERY TIME ────────────────────────────────────────────────┐ │ user query → embed → similarity search in ChromaDB │ │ → top-k relevant books (RETRIEVAL) │ │ → build context prompt │ │ → Ollama / Llama 2 reasoning (GENERATION) │ │ → ranked BookRecommendation list (with scores) │ └──────────────────────────────────────────────────────────────┘

Figure 3 — The two phases of the RAG pipeline.

8.1 Indexing

Each active book is converted into a descriptive text document combining its title, author, category, description, tags, publisher, and year. These documents are embedded into 384-dimensional vectors using the all-MiniLM-L6-v2 sentence-transformer model and stored in a ChromaDB collection. Embeddings capture semantic meaning, so conceptually similar books cluster together even when they share no exact keywords.

8.2 Retrieval

At query time, the user's natural-language request is embedded with the same model and used to perform a similarity search against the collection. The most semantically similar books are retrieved along with a distance score, which is converted into an intuitive match percentage shown in the UI.

8.3 Generation

The retrieved books are assembled into a context block and supplied to the Llama 2 model through Ollama, prompting it to explain why each book matches the user's intent — augmenting raw search results with human-readable reasoning.

8.4 Personalised Recommendations

For the "Recommended for you" feature, the system inspects the user's reading history, derives their dominant categories and authors, and synthesises an internal query describing those interests. That query is then run through the same retrieval pipeline, so personalisation reuses the core RAG machinery rather than duplicating it.

9. Fallback & Graceful Degradation Strategy

A defining engineering characteristic of the recommendation subsystem is its resilience. AI components (an embeddings model, a vector store, and an LLM runtime) are heavy and may be unavailable — for example, on a machine where Ollama is not running. Rather than failing the request, the system is designed to degrade gracefully through a tiered fallback chain, always returning something useful.

TierConditionBehaviour
1 — Full RAGEmbeddings + ChromaDB + Ollama all availableSemantic retrieval with LLM-generated reasoning.
2 — Retrieval onlyOllama unavailableReturns semantically ranked books from the vector store; the LLM step is skipped without error.
3 — Popularity fallbackEmbeddings model fails to load, or no reading history existsReturns the highest-rated available books from the database.
4 — Safe empty responseAn unexpected error occurs anywhere in the pipelineReturns a well-formed empty result instead of a 500 error, so the UI stays functional.
Why this matters. The fallback chain decouples the availability of the core library system from the availability of the optional AI infrastructure. Students can always browse, borrow, and receive at least popularity-based suggestions, even on a deployment that has no GPU or no model installed. Each degradation is logged for observability.

Comparable defensive handling is applied elsewhere: the embeddings model is wrapped in a try/except at start-up so a missing model never crashes the server, and the recommendation endpoints translate internal failures into a clean 503 Service Unavailable with a user-friendly message.

10. Frontend Implementation

The client is a React single-page application organised around pages, reusable components, global stores, and a service layer.

Structure & State

  • Service layer (Axios): a single configured Axios instance centralises the API base URL and attaches the JWT to outgoing requests, so authentication is handled in one place rather than per-call.
  • Global state (Zustand): lightweight stores hold authentication state, the book catalogue, loans, and recommendations, avoiding prop-drilling without the boilerplate of heavier state libraries.
  • Protected routing: a ProtectedRoute wrapper redirects unauthenticated users to the login page, and the navigation bar adapts to the user's role — staff see loan-management links while students see "My Loans" and "AI Recommendations".

Role-Aware Experience

RolePrimary interface
Student / FacultyBrowse and borrow books, track personal loans, view and download collection QR codes, request returns, and explore AI recommendations.
Librarian / AdminAdd/manage books and review the loan queue — approving or rejecting borrow requests and confirming returns from a tabbed management dashboard with live counts.

User Experience Details

  • Toast notifications give immediate feedback on every action (request submitted, approved, return confirmed, errors).
  • Optimistic, in-progress button states ("Requesting…", "Confirming…") communicate latency clearly.
  • Skeleton loaders and empty states keep the interface informative while data loads.
  • A responsive Tailwind layout with a glassmorphism theme works across desktop and mobile.
